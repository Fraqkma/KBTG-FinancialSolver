# Canonical demo — PM-1.1

This is the single numeric source for the **next MVP implementation**, fixture, API examples and tests. It deliberately supersedes Phase 1's 32,000/12,600/6,400 fixture. This documentation pass does not replace runtime seed data or test expectations; migration is one coordinated acceptance gate in [Integration plan](INTEGRATION_PLAN.md).

All names/services are fictional. User `demo-alex` (Alex, synthetic working adult). Currency THB. Period September 2026, Asia/Bangkok, baseline as-of `2026-09-25T09:00:00Z`. Salary was received September 1; the UI must not say it arrived today on September 25. Global Normal, no per-goal overrides, enabled=true, buffer 2,000. Policy PM-1.1 uses three complete history months, emergency multiplier 3 and recovery horizon 6.

## 5. Scenario B — financial shock

Branch from A immediately after confirmation, before any planned saving is realized. An urgent family medical event of **24,000** occurs at `2026-09-25T09:05:00Z`. Two synthetic posted expense rows share event `emergency-medical-1`: `shock-emergency` −18,000 from emergency, and `shock-daily` −6,000 from daily. Category Essential / Emergency medical, `is_emergency=true`, explicitly user-confirmed. These are expense parts, not a transfer plus a duplicated full expense.

This fixture represents an already paid event. The app did not execute the payment. An unconfirmed-emergency variant can leave the tag unresolved to exercise the clarification state, but the cash outflow is always real within the fixture.

```text
Emergency balance       18,000 − 18,000 =      0
Daily cash              18,900 −  6,000 = 12,900
Total assets            58,900 − 24,000 = 34,900
Upcoming costs                                 1,900
Cash buffer                                    2,000
Revised allocatable     12,900 − 1,900 − 2,000 = 9,000
```

Essential period total now 36,000 (12,000 normal + 24,000 emergency). This 36,000 is an expense total, not the emergency target. Normal costs remain 15,000; all period consumption including upcoming is 39,000. Current period disposable capacity is −9,000; history is still 14,000. This is consistent with using 18,000 of previously saved assets. Actual posted spending is 37,100. The one-off emergency event is excluded from Protected Monthly Outflow, so the average stays 13,500, target stays 40,500 and coverage is 0.00 months.

| Remaining allocation | Prior A | B proposal | Explanation |
| --- | ---: | ---: | --- |

Generate version 2 with a changed state revision. Conditional laptop completion moves December 2026 → May 2027 if 2,250 repeats (`ceil(20,000/2,250)=9` months). Moving has no forecast while contribution is zero. Both dates can improve after future recalculation.

These variants test constraint strength without changing A/B/C. Use September, the same goal gaps/deadlines, and zero realized period contributions. Global Normal; moving has an explicit Serious override, laptop remains Normal. **No prior confirmed commitment exists.** At B's post-shock balances/capacity, recovery remains 6,750 before either goal.

| Unallocated | 0 | 0 | 500 |

Serious moving receives its 1,000 request before the earlier-deadline Normal laptop. Laptop's conditional completion is December 2027 at 1,250 (`ceil(20,000/1,250)=16` months); moving stays February 2027 at 1,000. In the manual preview, moving 1,000 → 500 delays its conditional completion to August 2027 (`ceil(6,000/500)=12` months). State that the Serious contribution is changing, show the 500 reduction and timing, and use one normal Confirm. Unspecified amounts stay unchanged. Mode is neither a money lock nor a second confirmation gate.

For an infeasible Serious request, use a separate variant with an additional posted 1,750 expense from daily (daily 11,150; total assets 33,150; allocatable 7,250). Required cash remains 3,900 and recovery still receives 6,750. Moving Serious receives only 500 of its 1,000 request, laptop and General Savings receive zero, unallocated zero. Explain the 500 shortfall and August 2027 conditional moving completion. Serious cannot outrank protection/recovery or fabricate the missing capacity. With allocatable below 6,750, emergency recovery takes that capacity and Serious receives zero with no completion forecast.

For General Savings, global Serious with both goals explicitly Normal at A's cash gives a first-period request `14,000−3,750−5,000−1,000=4,250`, no prior confirmation or target/date/description required. It occupies the Serious saving tier. A distinct continuity example at B's cash with an existing General Savings baseline of 1,000 funds emergency 6,750, Serious General Savings 1,000, Normal laptop 1,250 and moving zero. Reducing General Savings to 500 is allowed: other amounts stay, unallocated becomes 500 and projected General Savings falls from 7,000 to 6,500. Show this balance consequence; there is no invented completion date for undated savings. General Savings follows global mode with no extra override field.

## 9. Reproducibility and test handoff

Data produces a deterministic base seed plus explicit local scenario branches. Re-seeding is an intentional local developer operation, never a public destructive reset endpoint. IDs, clocks, input revisions and confirmation times above are fixture values. Runtime IDs/times may differ; amounts, policy outcomes and lifecycle must match. Canonical setup must be idempotent and must not reset live user edits on ordinary startup.

Frontend and API tests consume the same seed/expected contract fixture; do not hand-copy divergent numbers into JSX. Assert account conservation, signed ledger totals, unique savings assignments, paid/upcoming reconciliation, A/B/C sums and projected coverage, exact version confirmation, post-restart history, unchanged cash on confirm, historical mean and conditional timelines. Include §8's first-period Serious priority, infeasibility and one-confirm override expectations. PM-1.1 verifies these as specification equations; executable implementation tests belong to the next workstreams.
